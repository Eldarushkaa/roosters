# API v1 · правила боя v8

Префикс маршрутов — `/api/v1`; версия боевых правил меняется независимо от него.
Время — Unix seconds, денежные поля с суффиксом `_minor` — **целые сотые доли
монеты**: `1000` означает ставку 10. Клиент не округляет баланс до целых монет.

POST принимает JSON-объект. Закрытые методы требуют
`Authorization: Bearer <token>`. Для всех команд, кроме входа, обязателен
`Idempotency-Key: <UUID>`. Повтор после потерянного ответа отправляет тот же
ключ, маршрут и JSON. Тот же ключ с другим содержимым даёт
`409 idempotency_conflict`.

Успешная команда возвращает `{result, state}`: результат операции сохраняется,
а `state` при повторе вычисляется заново. Ошибка имеет вид
`{error: {code, message}}`; сообщение предназначено игроку.

## Методы

| Метод и путь | Точный JSON запроса | Ответ / действие |
| --- | --- | --- |
| `GET /config` | — | `{dev_auth, bot_username, rules_version}`, без входа |
| `POST /auth/dev` | `{user_id, name}` | `{token, state}`; только локальная разработка |
| `POST /auth/telegram` | `{init_data}` | `{token, state}`; исходная подписанная строка Telegram |
| `GET /state` | — | Актуальный state; может завершить истёкшие бои |
| `GET /battle/quote?stake_minor=N` | Одна целая сумма в query, без JSON и UUID | Точная котировка доступной ставки, только чтение |
| `POST /presence` | `{}` | `result: {ok: true}`; обновляет присутствие и срок очереди |
| `POST /claim/passive` | `{}` | `result: {payout_minor}` |
| `POST /claim/daily` | `{}` | `result: {payout_minor}` |
| `POST /gear/upgrade` | `{slot}`: `helmet`, `armor` или `sword` | `result: {slot, level, cost_minor}` |
| `POST /breed/buy` | `{breed_id}` | Покупает/выбирает породу; `result: {breed_id}` |
| `POST /battle/start` | `{mode: "bot", stake_minor, expected_power}` | `result: {battle_id}` |
| `POST /queue/join` | `{stake_minor}` | `result: {matched: false}` либо `{matched: true, battle_id}` |
| `POST /queue/leave` | `{}` | `result: {ok: true}` |
| `POST /battle/tap` | `{battle_id, taps}` | `taps`: целое 1..90; `result: {accepted}` |
| `GET /leaderboard` | — | `{scope, power: [...], pvp_wins: [...]}` |

Дополнительные/пропущенные поля команды дают `invalid_payload`. `train` и
новый режим `practice` не поддерживаются; стойки в API отсутствуют.

В `POST /auth/telegram` приглашение берётся только из подписанного `start_param`
в `init_data`. При первом входе нового пользователя по действительному коду
пригласившему начисляются 300 монет; повторный вход и вход существующего
пользователя бонуса не дают. После трёх завершённых боёв друга (включая первый
бесплатный, тренировку и онлайн, независимо от исхода) пригласившему начисляются
ещё 300 один раз. Оба бонуса видны в его следующем `GET /state`; отдельной команды
получения нет. Разработческие аккаунты в приглашениях не участвуют.

Платные ставки — целые сотые доли монеты от `1000` до
`economy.stake_limits.max_minor`, шаг `1`. Пресеты `1000, 2500, 5000, 10000`
остаются быстрыми кнопками, но не ограничивают допустимые суммы.
`1001` означает 10,01 монеты, а JSON `1001.0`, строки и `true` отвергаются.
Только `battle/start` допускает
`stake_minor: 0`, пока `economy.first_free_battle_available` истинно.
Любой первый начатый бой расходует это право. Ставка 0 даёт фиксированную
награду 1500 независимо от исхода; это не обычный приз и не RTP.

`expected_power` должен быть целым и совпадать с текущей серверной мощью.
Он защищает выбор ставки после изменения мощи в другой вкладке; сервер сам
определяет мощь и приз. При расхождении возвращается `409 power_changed`:
нужно обновить состояние и заново подтвердить запуск.

```json
      {"stake_minor": 10000, "win_payout_minor": 24000}

  "presence": {"online": 0, "searching": 0, "development_online": 1},
  "queue": null,
  "battle": null,
  "reward_events": [],
  "history": []

```

В ответе также всегда есть `catalog`: `coin_scale: 100`, `breeds` с
`price_minor`, `power_multiplier` (1 / 1.2 / 1.5 / 1.9) и целым
`power_multiplier_percent` (100 / 120 / 150 / 190), `slots`, `battle` и `referral`.
У породы больше нет поля фиксированной `power`: множитель применяется ко всей
сумме базы, уровня и экипировки с округлением вниз один раз.
`slots[].power_per_level` задаёт прирост базовой мощи до множителя породы.
`catalog.referral` содержит серверные условия для описания приглашения:

```json
{
  "signup_reward_minor": 30000,
  "battle_reward_minor": 30000,
  "battles_required": 3
}
```

`catalog.battle` имеет вид:

```json
{
  "duration": 10,
  "roulette_duration": 2,
  "tap_cap": 90,
  "tap_bonus_cap": 0.2,
  "stakes_minor": [1000, 2500, 5000, 10000],
  "bot_power_min_ratio": 0.7,
  "bot_power_max_ratio": 1.4,
  "bot_rtp_min": 0.9,
  "bot_rtp_max": 1.2,
  "pvp_win_multiplier": 2.4,
  "pvp_rtp": 1.2,
  "free_reward_minor": 1500
}
```

`reward_events` — до 20 последних выплат текущего игрока из `coin_ledger`,
новые первыми (по убыванию `id`, включая события с одинаковым временем).
В список входят только `referral_signup` (вход друга), `referral` (бонус за бои
по приглашению) и `battle_reward` (выплата за собственный завершённый бой):

```json
{
  "id": 42,
  "reason": "referral_signup",
  "amount_minor": 30000,
  "created_at": 1800000000,
  "friend_name": "Петя"
}
```

`friend_name` — текущее имя приглашённого для бонусов пригласившему;
для собственных боёв и старых реферальных бонусов самому приглашённому — `null`.
Для `battle_reward` сумма — валовая выплата, включающая ставку при победе;
нулевые выплаты при поражении тоже показываются. Это не чистое изменение баланса.
Журнал возвращается со state при входе, обновлении и командах; отдельного
начисления, локального накопления событий или доступа к чужим выплатам нет.

`tap_bonus_cap` описывает прибавку эффективной мощи в PvP. Формула ботов
отдельная: [игровой дизайн](GAME_DESIGN.md#бой-с-ботом).
`bot_quotes` — границы фиксированного приза при текущей мощи, а не сумма
выигрыша выбранного будущего соперника. Точный приз приходит в `battle.wager`.
`online_quotes` — серверные персональные призы для каждой быстрой ставки;
интерфейс берёт сумму из этого массива без вычисления денег через дробный
множитель. `catalog.battle.stakes_minor` описывает быстрые кнопки;
`economy.stake_limits` задаёт весь допустимый диапазон ползунка. Обычно
`max_minor` равен балансу; если баланс ниже минимума, `max_minor < min_minor`
и платный запуск недоступен. Готовые `bot_quotes`/`online_quotes` сохраняются
для пресетов, включая временно недоступные по балансу.
`pvp_win_multiplier` описывает выплату относительно собственной ставки и
заменяет `pvp_pool_return`: общий возврат банка не гарантируется.

В `player.wins` остаются все победы. Для рейтинга живого PvP использовать
`pvp_wins`, который исключает ботов и аккаунты разработки.
`upgrade_costs_minor[slot]` равен `null` на максимальном уровне предмета.

## Котировка произвольной ставки

`GET /battle/quote?stake_minor=12345` требует авторизацию, но не
`Idempotency-Key`. Ответ при мощи 100:

```json
{
  "rules_version": "v8",
  "power": 100,
  "stake_minor": 12345,
  "bot": {"min_payout_minor": 18887, "max_payout_minor": 26665},
  "online": {"win_payout_minor": 29628}
}
```

Метод не запускает maintenance, не завершает просроченные бои, не создаёт
команды и не меняет кошелёк или право первого боя. Он читает текущую мощь и
баланс в одном снимке базы. Разрешён ровно один query-параметр `stake_minor`
из ASCII-цифр; повтор ключа, лишние поля, дробь, знак и exponent отвергаются.
Ставка 0 здесь недоступна. Недостаток средств даёт `409 insufficient_funds`.

Котировка не резервирует средства. При запуске сервер снова проверяет сумму,
баланс и `expected_power`, а в очереди — персональную ставку каждого игрока.
Клиент использует котировку лишь при совпадении ставки, мощи и версии правил
с текущим выбором; запоздалый ответ на прежнее положение ползунка игнорируется.

Технический потолок ставки — `floor((2^53 − 1) / 12)` сотых долей:
даже максимальный приз онлайн-боя `12 × ставка` остаётся точным JSON/JavaScript
целым. У исторического баланса, близкого к пределу SQLite `2^63 − 1`,
максимум дополнительно ограничивается запасом под чистый выигрыш:
`floor((2^63 − 1 − balance_minor) / 11)`. Поэтому окончательный
`max_minor` — минимум баланса и этих технических границ. Суммы и котировки
считаются целыми числами и `Fraction`, без расчёта денег через `float`.

## Очередь и присутствие

Очередь имеет вид `{joined_at, expires_at, stake_minor}`. Без обновления она
истекает через 60 секунд; heartbeat продлевает её максимум до 120 секунд от
начала поиска. Присутствие считается свежим 45 секунд. Видимому клиенту
достаточно посылать `presence` примерно раз в 15 секунд.

Пара состоит из аккаунтов одного типа (Telegram либо разработка). Кандидат
выбирается по времени ожидания без ограничений по мощности и ставке. При
создании матча сервер списывает с каждой стороны её собственную ставку;
средства кандидата сравниваются с его ставкой из очереди.
Выход и истечение очереди не требуют возврата, поскольку списания ещё не было.
Реальные `online` и `searching` не включают разработческие аккаунты.

## Состояние боя

`battle` и элементы `history` используют одну форму:

```text
{
  id, mode: "bot" | "online", status: "active" | "finished",
  rules_version, created_at, starts_at, ends_at, tap_cap,
  you: {name, power, breed_id, gear: {helmet, armor, sword}, taps},
  opponent: {name, power, breed_id, gear: {helmet, armor, sword}, taps, is_bot},
  wager: {stake_minor, win_payout_minor},
  roulette: null | {min_power, max_power},
  dynamic_payout: boolean, // true for online v8
  tap_analysis: null | {you: {taps, initial_probability, final_probability, change},
                        opponent: {taps, initial_probability, final_probability, change}},
  current_win_probability: null | number, // server odds from accepted taps, v3..v8
  win_probability: null | number,
  result: null | {won, xp, payout_minor, net_minor}
}
```

`breed_id` и `gear` фиксируются при создании боя вместе с мощью. У игроков
это выбранная порода и точные уровни каждого предмета; последующая покупка
или улучшение не меняет внешний вид бойца в сохранённом бою и истории.
У бота `gear` — сохранённый визуальный комплект: одинаковый уровень предметов,
соответствующий уже выбранным сервером породе и мощи при нулевом XP.
Комплект не пересчитывает мощь бота и не влияет на шанс, выплаты или случайный
исход. В старых сохранённых боях `gear` может отсутствовать: клиент показывает
базовый вид без экипировки, а не подставляет текущую экипировку игрока.

У бота `roulette` задаёт диапазон анимации; точный соперник уже сохранён
в `opponent`. `created_at` — начало двухсекундной подготовки,
`starts_at` — начало 10-секундного боя. Состояние до `starts_at` тоже
называется `active`; отдельного изменяемого состояния «рулетка» нет.

`wager.win_payout_minor` **включает ставку**. У бота он фиксирован до боя.
У онлайн-боя v8 (`dynamic_payout: true`) он пересчитывается по текущим кликам,
а при завершении сохраняется по итоговому шансу: `floor(1.2 × ставка / p)`.
До подбора `online.win_payout_minor` и `online_quotes` — пример при шансе 50%,
не обещание фиксированной выплаты. `pvp_win_multiplier` также относится к 50%.
`wager` всегда относится к текущему игроку, в том числе в `history`: две
стороны online-боя могут получить разные `stake_minor` и `win_payout_minor`.
Для v5..v7 online приз равен `floor(1.9 × собственная ставка)` и не зависит от
ставки противника. Мощь и клики меняют шанс и матожидание, а не этот приз.
`result.payout_minor` — реально зачисленная сумма,
`result.net_minor = payout_minor - stake_minor`.
В бесплатном первом бою обе суммы равны 1500 при любом исходе.
Для платного поражения `payout_minor` равен 0.

Случайное число не выдаётся клиенту. Итоговая `win_probability` раскрывается
после расчёта и относится к стороне текущего игрока. До расчёта это `null`.
`current_win_probability` — число от 0 до 1 по сохранённым мощностям и принятым
кликам для v3..v8; у v1/v2 это `null`. Поле вычисляется и во время подготовки,
но интерфейс показывает его после `starts_at`. В PvP оно учитывает клики
обоих игроков. Это вероятность победы, а не RTP; случайное число и будущий
результат остаются скрытыми. После завершения сохраняется итоговая
`win_probability` по стороне игрока.
Закрытие приложения не отменяет бой. Последний бой остаётся в state до нового,
история содержит до десяти завершённых боёв.

Касания v4..v8 принимаются только при `starts_at <= server_time < ends_at`.
Лимита скорости нет: одна пачка может содержать все 90. Общий предел считается
сервером для каждой стороны; `accepted` может быть меньше отправленного.
До старта возвращается 0, после конца — `409 battle_finished`.
Повтор ключа возвращает исходное `accepted` и не добавляет клики снова.
Размер запроса ограничен 1..90, а остаток полезных кликов определяется
`battle.tap_cap` выбранного движка: в сохранённом v3-бою это по-прежнему 80.

## Рейтинги

`scope` равен `telegram` или `development`. Каждый из массивов `power`
и `pvp_wins` содержит до 50 строк:

```text
{id, name, power, pvp_wins, level}
```

Первая таблица сортируется по мощи, затем по PvP-победам; вторая наоборот.
Последний критерий — стабильный `id`. Реальные рейтинги исключают аккаунты
разработки. Разработческие матчи не увеличивают `pvp_wins` даже в локальной таблице.

## Совместимость и ошибки

`state.rules_version` и `catalog` описывают текущие правила v8. При этом
`battle.rules_version` может оставаться `v3`, `v4`, `v5`, `v6` или `v7`: такие бои сохраняют
прежние снимки мощи, приз и формулу шанса. У v3 лимит 80 кликов; у v4 — 90
и прежний верхний RTP бота 105%; у v5/v6 — 110%, у v7 — 120%. Для интерфейса исторического боя нужно
использовать `battle.tap_cap` и сроки самого боя, а не подставлять лимит 90
из нового каталога. Миграция 005 копирует общую ставку и приз прежних online
боёв в поля второй стороны, не меняя уже сохранённые условия и результаты.
Для v6 новая миграция не нужна: расширение ставок не меняет сохранённые
условия v5, его движок остаётся в реестре. V7 также не требует миграции:
движок v6 сохранён для завершения начатых боёв с прежним RTP.

Старые бои v1/v2 возвращаются с исходным `rules_version`, своим `tap_cap`
и временем. Возможны исторический `mode: "practice"`, поле `stance` в
снимке и `coins/medals/legacy` в результате. Их нельзя трактовать как новые
команды: UI использует нормализованные `payout_minor/net_minor`.
Старые успешные UUID/JSON продолжают возвращать сохранённый результат
операции; свежий state всегда использует текущий контракт v8. Старую страницу
после обновления сервера нужно перезагрузить.

Типичные коды: `401 unauthorized`, `400 invalid_payload`,
`400 invalid_stake`, `400 invalid_taps`, `409 insufficient_funds`,
`409 player_busy`, `409 free_battle_used`, `409 power_changed`,
`409 battle_finished`, `409 daily_not_ready`, `409 idempotency_conflict`.
После timeout/5xx повторять исходную команду с прежним UUID; новый ключ
не является способом проверить, была ли уже выполнена операция.

`tap_analysis` доступен после завершения онлайн-боя v3–v8 в `battle` и
`history`. Все вероятности/изменения заданы долями единицы; для процентных
пунктов `change` умножается на 100. До боя и для ботов/legacy v1–v2 — `null`.
V8 не требует миграции; завершение v7 выбирает сохранённый движок.
